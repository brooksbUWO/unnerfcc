@internal A harness-observed shell command changed repository state. This covers git commit, cherry-pick, push, merge, and rebase. It excludes dry runs. The event is a cache-invalidation signal with a minimal payload. Beyond the classification, it carries two hints about where to look: the branch that was acted on, and the directory the shell finished in. Consumers still re-read state (head, PR status) from the repository. They do not decode the event for that state. The event comes from the same detection as the tool result's structured gitOperation data. The two agree on what happened. Only a push's `branch` is attributed more strictly here than in that data. This attribution comes from the push's own output section. A compound command can emit more than one kind. A merge and a rebase in one command collapse to the latter. You can coalesce these freely. The event is best-effort, not exhaustive. It observes only foreground mutations that run through the Bash or PowerShell tools. If a backgrounded command's confirming output had not printed at capture time, the command emits nothing. A foreground push whose ref lines were redirected or silenced still emits. It emits on the invoking command's zero exit code alone. Thus a compound that swallows a failed push's exit code also emits. The event is a prompt to look, never a claim.
